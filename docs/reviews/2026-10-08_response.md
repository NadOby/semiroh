## Bootstrap findings

### F3. D4 should constrain D3

- **Verdict:** confirmed. Fix by wording; no re-order.
- **Evidence:** the roadmap frames D3 as trust versus speed ("about 150x the
  host machine per layer"). On D4's recommended workload, route (a)'s larger
  cost is coverage:
  - The SHEAR VM runs a pure subset (`vm._ORDER`, vm_in_shear §2). It does not
    interpret READ, WRITE, CODE, LINKS, CATCH, FAIL or RAISE (§4), nor QUOTE,
    FUNCTION, ACTIVATE or TRIAL.
  - `activate`, `read`/`write`, `code` and `linksof` resolve their target
    through the running function's static links (metaprogramming §4,
    self_hosting §1). Interpreted code runs inside `vm_run`, so it would need
    targets chosen by value, which is Open with a capability concern
    (vm_in_shear §8: "Cells from the interpreter", "CODE and LINKS by
    reference").
  - The VM's CALL is `applyv` on the installed callee (`direct_call` in
    `vm.py`), which runs the callee's host-lowered chunk unless the callee is
    a wrapper. Route (a) without host lowering therefore means wrapping every
    function of every corpus program: task 27's wrappers with literal chunks
    across the corpus, against the first acceptance anchor.
  - Route (b) needs none of this, since the host machine runs every
    instruction, but needs node identities in the compiler's view
    (self_hosting §6, Open) and a verifier (F5).
  - Time: generation 1 (compiler on the host machine) took 0.86 s here, of
    which 0.58 s was `define` for the activation and 0.05–0.07 s the SHEAR
    compiler itself. Generations 2 and 3 on the SHEAR VM took 21 s each on CI
    (vm_in_shear §7). End to end that is about 18x, not 150x, and permitted
    host services dominate the fast route.
- **Consequence:** compared on today's compiler, route (a) looks like "slower
  but trusted". On D4's workload it needs new by-value access semantics and
  wrappers over the whole program.
- **Smallest action:** task 29: "Compare the routes on D4's recommended
  workload using task 28's matrix; for route (a), include the instructions the
  SHEAR VM lacks and the by-value targets they need (vm_in_shear §8)." D4's
  workload half already has a recommendation for task 29 to use; D3 and D4's
  host boundary are decided together after task 29, because the boundary
  depends on the route.

### F5. The verifier needs a stated rule

- **Verdict:** confirmed.
- **Evidence:** "verifier" occurs twice in the repository, roadmap D3 and
  task 29, undefined. A host chunk is "a function of its node's value alone"
  (bytecode §2), so the obvious check, equality with host `lower(node)`, makes
  the SHEAR compiler's output redundant. It also puts host lowering into
  admission, which task 30's "provenance shows no host lowering for executed
  code" forbids.
- **Refinement:** for per-node chunks with children by `EntityID`, dependency
  freshness is not a verifier concern: "a chunk is valid for as long as its
  value exists" (bytecode §5) and calls resolve at run time. Admitting a chunk
  for node N at version V comes down to:
  - well-formed instructions;
  - child operands name N's own code children;
  - entity operands (CALL, REF, CODE, LINKS, READ, WRITE) are links of N's
    owner;
  - the producer is recorded.

  Compiler correctness stays with the differential tests (self_hosting §3).
- **Smallest action:** task 29, done-when: "and states the admission rule for
  a chunk of node N at version V, without host lowering".

    being detected.
