On the broader design material, I mostly agree with the peer.

The critique of the canaries is good. My phrase “several unrelated canaries” needed a stronger independence condition. Eleven canaries all failing because the language currently cannot create application-defined semantic structures are not eleven independent pieces of evidence. They share one prerequisite. The useful rule is closer to:

> Repeated failures count as evidence for a missing core abstraction only when the canaries exercise genuinely independent requirements rather than sharing the same deferred prerequisite.



I would preserve the canaries, though. They should be treated as future probes blocked by particular prerequisites, rather than current acceptance requirements. Keeping the original dated document under docs/reviews/ while later adding a much smaller “design canaries” section to corpus.md seems reasonable.

On the design goals, the peer identified an important mistake in my document: I accidentally weakened SHEAR from a systems programming language to merely “a programming language with a reflective, evolvable semantic program model.” I agree with the rebuttal. Do not adopt that wording. Systems programming remains part of the project identity.

The genuinely new goals are also correctly identified:

- Lisp/Forth-like language malleability;
- cheap DSL construction;
- independently developed semantic libraries composing through ordinary language mechanisms;
- unusual applications should normally require libraries, not new core primitives.

Those are not consolidation of existing documentation – they are new direction. But from this conversation you have already answered the owner question: yes, those are goals. I would record them as provisional long-term goals in the existing README design-philosophy/metaprogramming material, explicitly without changing current roadmap priority.

The graph-hypothesis/object-image comparison belongs in graph_ledger.md, as the peer suggests. That is much better than creating architecture_hypotheses.md.

On the velocity note, I think the peer improved my formulation. In particular this qualification is worth keeping:

> An experiment buys evidence only if the discriminator is chosen before the run and is mechanical enough to decide something; otherwise cheap implementation merely produces two implementations that must still be compared by argument.



So I would preserve both principles:

> Exploit cheap implementation to buy evidence rather than accumulate implementation.



> When bounded competing implementations can resolve an architectural uncertainty, prefer the experiment – but specify the discriminator before implementing them.



I would not generalize the “one revision” rule to every architectural experiment. That is useful discipline for tightly scoped research tasks, but some experiments legitimately expose instrumentation problems or an incorrectly formulated discriminator. Predictions-before-run and explicit falsifiers are the important general rules; revision count can remain task-specific.
